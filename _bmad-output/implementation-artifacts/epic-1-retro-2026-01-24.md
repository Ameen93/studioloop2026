## What Went Well

### 1. Consistent Architecture Patterns Established
- Every endpoint follows ARCH-28 error format with `code`, `message`, `details`
- All API/DB fields use `snake_case` per ARCH-24/25
- Password hashing migrated to Argon2 per ARCH-11 with backward bcrypt compatibility
- JWT tokens use <24h expiry with refresh rotation per ARCH-12

### 2. Test Coverage Maintained High Standards
- 220+ backend tests by epic completion
- Every story added comprehensive API tests
- Test utilities established: `random_email()`, `create_consumer_with_token()`, `create_verified_consumer()`
- Mocking patterns for email sending and OAuth responses documented

### 3. OAuth Implementation Reuse
- Google OAuth patterns (Story 1.9) directly reused for Apple (Story 1.10)
- Authlib abstraction worked well for both providers
- Account linking logic shared: check by provider ID, then by email
- SessionMiddleware for CSRF protection applied to both flows

### 4. Security-First Design
- No-enumeration patterns on forgot-password and login (same response for valid/invalid emails)
- Token version increment invalidates all sessions on password reset and account deletion
- Password confirmation required for account deletion (prevents CSRF attacks)
- Email verification required before login

### 5. Cross-Platform Consistency
- Web and mobile screens follow same UI patterns (Warm Earth theme)
- Same API client used across all frontends via Hey API generation
- MMKV for mobile, localStorage for web - both work with same token structure

## Challenges & Learnings

### 1. OAuth Callback Differences
- **Google**: GET callback with query params
- **Apple**: POST callback with form data (`response_mode=form_post`)
- **Apple**: Client secret is a dynamically generated JWT, not static
- **Lesson**: Read provider docs carefully; OAuth is not standardized

### 2. First-Login Name Handling (Apple)
- Apple only provides user's name on the FIRST authorization
- Subsequent logins return no name data
- **Lesson**: Store name immediately on first OAuth; fallback to "Apple User" if missed

### 3. Hide My Email Complexity
- Apple relay emails (@privaterelay.appleid.com) must be accepted
- These are valid emails that forward to real addresses
- **Lesson**: Never reject emails based on domain; trust the OAuth provider

### 4. Token Version Migration
- Added `token_version` field in Story 1.4 for refresh token rotation
- Required migration and updating all token generation/validation
- **Lesson**: Design token invalidation strategy early; retrofitting is harder

### 5. Frontend OAuth Integration
- Initially had placeholder buttons with no functionality
- Fixed by adding proper redirects to backend OAuth endpoints
- Mobile uses `Linking.openURL()`, web uses anchor tags
- **Lesson**: OAuth is server-initiated; frontend just redirects to backend

### 6. Staff vs Consumer Auth Separation
- Staff and consumers use different auth endpoints (`/auth/consumer/*` vs `/auth/staff/*`)
- JWT claims include `type: consumer` or `type: staff` for validation
- **Lesson**: Separate user types clearly; don't mix auth flows

## Key Insights

1. **OAuth abstraction (Authlib) pays off** - Adding Apple took half the time of Google
2. **Token version is essential** - Password reset and deletion require session invalidation
3. **No-enumeration is non-negotiable** - Security requires identical responses for valid/invalid inputs
4. **POPIA compliance requires planning** - Soft-delete first, hard-delete after 30 days (deferred job)
5. **Email verification gates login** - Unverified accounts cannot authenticate
